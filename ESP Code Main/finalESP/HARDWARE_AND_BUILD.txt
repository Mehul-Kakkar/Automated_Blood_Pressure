Hardware findings and build/provisioning notes

Pin map used by the integrated `finalESP` firmware (per the requested final wiring):
- Microphone ADC: GPIO10, nominal 2 kHz sampling. Firmware removes baseline drift, applies a 20–300 Hz biquad bandpass, smooths an 8 ms envelope, and detects individual acoustic candidates against a bounded adaptive noise threshold. The phone receives sequenced 2 kHz BLE batches with filtered signal, envelope, and threshold; MQTT sends a 50 Hz decimated trace plus structured candidate events. These settings are experimental, and no clinical detection performance is claimed. GPIO4 remains pump IN2. The older `korotkoffDebug` sketch and amplifier note identify GPIO4 and are legacy references, not the integrated pin assignment.
- DSP verification/replay uses the exact portable detector header without Python: compile `tests/korotkoff_synthetic_test.cpp` for synthetic cases, or compile `tests/korotkoff_replay.cpp` and pass a text/CSV file containing one raw ADC count (0–4095) per line. Replay reserves the first 4 seconds for pressurized-cuff calibration and then enters deflation mode; it writes filtered signal, envelope, threshold, and candidate events as CSV.
- HX710B OUT/SCK: GPIO8/GPIO9 (`pumpvalveTest.ino`); the main firmware uses the installed `hx710b_arduino` library and exposes the supplied rough mmHg estimate as estimate-only.
- L298N pump IN1/IN2/EN: GPIO5/GPIO4/GPIO15 (`pumpvalveTest.ino`). Microphone input is GPIO10; pump IN2 on GPIO4 is configured as an output.
- L298N valve IN1/IN2/EN: GPIO6/GPIO7/GPIO16 (`pumpvalveTest.ino`). The valve is normally open: firmware energizes it closed for inflation and passive deflation, then de-energizes it at/below 60 mmHg to open the exhaust fully. A hard pressure fault also de-energizes it for emergency release.

The configured empirical decreasing-pressure calibration is `-1.622066 + 0.00001132803915 * centered_counts` mmHg. Centered counts are `hx710b_arduino`'s returned offset-binary value minus 8,388,608, matching `Centered_Counts` in `sensorCalibration.ino`; the library's XOR is not applied a second time. Centered signed saturation endpoints are never converted to pressure. Saturation ends inflation without a fault: the pump stops, the valve stays closed for at least one second, then passive backflow continues until the valid pressure reaches the normal valve-release threshold. Other implausible/stale sensor readings retain their safety-stop behavior. Calibration covers approximately 75–92 mmHg and is not clinically validated. Timed pump mode is disabled and prohibited by a compile-time assertion because it bypasses pressure feedback.

The integrated session flow inflates to the configured target with a firmware hard cutoff: pump OFF with the normally-open exhaust valve energized CLOSED, then passive pump-backflow deflation. At/below the configured release threshold the firmware de-energizes the valve for full exhaust. This is unvalidated bench behavior and requires mechanical pressure relief and independent hardware validation. The nominal amplifier note calculates a gain of 5.7 and a divider output centered near 1.67 V, but these are design calculations only; this repository contains no measured gain, ADC waveform, clipping margin, or labelled acoustic recordings. Confirm the physical amplified output voltage at GPIO10 and verify it remains in the ESP32-S3 ADC input range before connecting hardware.

Dependencies: Arduino-ESP32 core 3.x, PubSubClient 2.8.x, ArduinoJson 6.21.x. Compile/upload the `finalESP.ino` sketch folder for the exact ESP32-S3 board selected in Arduino IDE/CLI. The separate `DisplayCode/finalDisplay/finalDisplay.ino` needs Arduino-ESP32 core 3.x and ArduinoJson 6.21.x. Match the configured ESP-NOW channel on both boards and the Wi-Fi AP.

For the ESP32-S3 Dev Module with 4 MB flash, set **Tools > Partition Scheme > Huge APP (3MB No OTA/1MB SPIFFS)** before compiling and uploading `finalESP`. The default partition only provides a 1.2 MB app slot, too small for the BLE + TLS/MQTT firmware. This controller firmware does not use SPIFFS or OTA updates; USB serial flashing remains available. The partition setting affects the flash layout, so use the same setting for build and upload.

For MQTT, copy `secrets.example.h` to local `secrets.h` (the latter is git-ignored). Set `BP_DEVICE_ID` to the UUID returned by the backend, and `BP_MQTT_DEVICE_KEY` to the broker-enrolled principal (the supplied example is `bp_device_001`). Set that device account's password and keep the EMQX hostname `k7128701.ala.asia-southeast1.emqxsl.com` and port `8883`. Firmware validates the configured broker CA using `WiFiClientSecure`; provide the trusted EMQX CA PEM in `BP_BROKER_CA_CERT`. In EMQX Cloud, open the deployment's Overview page and download its CA Certificate; paste the PEM certificate into this macro, preserving the BEGIN/END lines and `\n` escapes. This certificate is public trust material, not a client certificate or private key. Never use plaintext MQTT or a skip-verification TLS mode. Wi-Fi credentials may instead be configured on the app's Device page over BLE; they are stored in ESP32 Preferences (NVS) and take precedence over the example compile-time defaults. The broker ACL must allow the backend identity to subscribe to `bp/devices/+/telemetry`, `bp/devices/+/status`, and `bp/devices/+/ack`, and publish `bp/devices/+/commands`. The device identity may publish only its own `bp/devices/{BP_MQTT_DEVICE_KEY}/telemetry`, `/status`, and `/ack`, and subscribe only to its own `/commands` topic. The payload `device_id` remains the backend UUID; the MQTT topic key is the enrolled broker principal. Firmware publishes are QoS 0 (PubSubClient limitation); commands/subscriptions use QoS 1 where supported. Messages are not retained.

The firmware includes a BLE phone command service and optional MQTT device transport. MQTT cloud commands require backend device enrollment, broker deployment, TLS credentials, and ACL configuration. A touchscreen ESP-NOW START without a backend `session_id` is held as a request; there is not yet a backend bridge that creates and returns that session ID. The display therefore cannot start a complete cloud-linked session by itself.
